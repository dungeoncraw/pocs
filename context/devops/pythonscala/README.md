# Django and Scala 3 Shared CSV APIs — Minikube

This project runs one Kubernetes Deployment with a single Pod and three
containers:

```text
Deployment: django-scala
└── Pod (1 replica)
    ├── django
    │   ├── Django + Gunicorn
    │   └── Python CSV API on port 8000
    ├── scala-api
    │   └── Scala 3 CSV API on port 9000
    └── scala-cron
        └── Supercronic runs the Scala update every 10 minutes
```

All three containers mount the same PersistentVolumeClaim at `/data`.

```text
/data/records.csv
/data/records.lock
```

The Python and Scala implementations use an operating-system file lock and
atomic file replacement. This prevents concurrent updates from reading the
same old CSV and overwriting each other's changes.

## CSV schema

```csv
id,name,value,updated_at,updated_by
```

The `id` field is the record key.

- When the ID does not exist, the API creates a row.
- When the ID already exists, the API replaces that row.
- `updated_at` and `updated_by` are generated by the application.

Both APIs support commas and quotes inside values. Line breaks are rejected
so each CSV record remains on one physical line.

## Matching APIs

### Django/Python

```text
POST /api/csv/upsert/
GET  /api/csv/records/
```

### Scala 3

```text
POST /api/csv/upsert
GET  /api/csv/records
```

Both POST endpoints accept:

```json
{
  "id": "customer-100",
  "name": "Example customer",
  "value": "active"
}
```

Both return the updated record, whether it was created, and the total number
of records in the shared CSV.

Install:

- Docker;

## Access the APIs manually

Start a port-forward for both Service ports:

```bash
kubectl port-forward \
  -n django-scala-local \
  service/django-scala \
  18080:80 \
  19000:9000
```

Keep that terminal open.

### Update through Django/Python

```bash
curl --request POST \
  --header 'Content-Type: application/json' \
  --data '{"id":"record-1","name":"Python update","value":"created by Django"}' \
  http://127.0.0.1:18080/api/csv/upsert/
```

### Read through Django/Python

```bash
curl http://127.0.0.1:18080/api/csv/records/
```

### Update through Scala

```bash
curl --request POST \
  --header 'Content-Type: application/json' \
  --data '{"id":"record-1","name":"Scala update","value":"updated by Scala"}' \
  http://127.0.0.1:19000/api/csv/upsert
```

### Read through Scala

```bash
curl http://127.0.0.1:19000/api/csv/records
```

## Scheduled Scala update

The scheduler executes:

```text
/opt/scala-job/run-job.sh
```

every 10 minutes:

```cron
*/10 * * * * /opt/scala-job/run-job.sh
```

The scheduled implementation calls the same Scala `CsvStore.upsert` function
used by the Scala HTTP API.

It creates a record with an ID similar to:

```text
cron-2026-07-26T16:30:00Z
```

Run it manually:

```bash
make run-scala
```

## Shared persistence

The CSV is stored in the `shared-csv-data` PersistentVolumeClaim.

```bash
kubectl get pvc -n django-scala-local
```

Restarting or replacing the Pod keeps the CSV because the file is not stored
in the container filesystem.

Deleting the namespace also deletes the PVC:

```bash
make down
```

## Architecture notes

### Why three containers?

`scala-api` runs one long-lived HTTP server process.

`scala-cron` runs Supercronic as its long-lived scheduler process.

Keeping these responsibilities in separate containers avoids starting an
HTTP server and a process scheduler inside the same container.

### Why a single replica?

Every Pod contains a scheduler. Increasing the Deployment replica count would
create multiple schedulers and duplicate scheduled executions.

For a horizontally scaled production Django deployment, move the scheduler
into a separate Kubernetes `CronJob`.

### Locking scope

The solution uses POSIX/JVM file locks on `/data/records.lock`. This is
appropriate for the single-Pod design because every writer accesses the same
mounted filesystem.

For multiple Pods writing concurrently, replace the CSV with a transactional
datastore or add a distributed lock.
